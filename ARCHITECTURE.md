# RAG-прототип для статистических докладов (docx)

## 0. Что показало исследование реальных файлов

- `Докл 0119.docx`: 801 абзац, **109 `<w:tbl>`**, но логических таблиц меньше — они
  разбиты на куски, между которыми идёт абзац **«Окончание»**. При сборе логической
  таблицы куски нужно **склеивать** (общий заголовок/номер таблицы).
- Шапки — многострочные, со слиянием ячеек. Одна «колонка показателя» на самом деле
  кортеж: `(период, тип метрики, базис)` — например:
  `Январь 2019 г. / в % к янв 2018 г.` = `{period: 2019-01, kind: abs}`,
  `в % к янв 2018` = `{kind: rel_yoy}`, `Справочно: январь 2018 г.` = `{period: 2018-01, kind: abs, ref: true}`.
- Единица измерения (Ед. изм.) встречается в **трёх местах**: шапка столбца («млн. руб.»),
  текст строки показателя («оплата труда, тыс. руб.»), надпись над таблицей.
- Дата публикации — заголовок первой страницы: `Январь 2019 года` → `pub = 2019-01`.
- `test-0119.json` / `test-0308.json` / `test-1219.json` — готовый набор
  «вопрос → (файл, таблица, ответ)». Это **акцепт-тест** прототипа.
- Объявлено 480+ таблиц на весь архив → индекс SQLite по ~2000–4000 «наблюдений»,
  легко влезает в память; векторные БД не нужны.

## 1. Выбор подхода: struct-first RAG (SQLite FTS), без векторов

Запросы «сколько / какой» требуют:
1. точного совпадения показателя (по смыслу, но по стрингу),
2. точного периода (нормализуемого до `(тип, год, месяц/квартал)`),
3. возвращать **число, единицу измерения, источник, месяц публикации**.

Векторный поиск не может гарантировать (1)–(2) для чисел. Эмбеддинги здесь — анти-паттерн
(см. «таблицы против текста» — см. ссылки в конце). SQLite + FTS5 при этом даёт:
- атомарность, инкремент, транзакции, `VACUUM`, резервные копии;
- FTS5 с `trigram`-токенизатором для поиски по русским именам показателей (без
  необходимости строить свой морфологический стеk);
- полный контроль дедупликации по нормализованным ключам (правило «позднее
  опубликованный выигрывает») в SQL-запросе, а не в LLM-потоке.

Дополнительно (опционально, для второго круга) — LLM-агент в режиме «переводчик»:
свободный вопрос → JSON `{indicator: "...", period: "...", kind: "abs|rel"}` → SQL.
На прототипе это — не критически, т.к. тестовые вопросы уже нормализованы.

## 2. Стек (Python)

| Задача | Библиотека | Комментарий |
|---|---|---|
| Чит docx | `python-docx` (+ `docx.oxml` для `w:gridSpan`/`vMerge`) | `python-docx` не читает вложенные таблицы и слияния напрямую — достаём ячейки через `w:tc` / `w:tcPr`. |
| Парсинг текста (периоды, Ед.изм.) | `re` + словари | месяцы, «в % к», «по сравнению с», «к предыдущему месяцу» — фиксированные шаблоны. |
| Хранилище | `sqlite3` (stdlib) + FTS5 | Включен в Python 3.9+, `trigram`-токенизатор. |
| Инкремент-хеш | `hashlib.sha256` | По содержимому файла, не по mtime (Syncthing/копии меняют mtime). |
| Конфиг | `pydantic` + `config.yaml` | Путь к архиву, путь к БД, пороги. |
| Тесты | `pytest` | `test-*.json` как golden. |
| Интерфейс | CLI (`argparse` / `typer`) | `index`, `search`, `stats`. REST — не нужен для прототипа. |

Опционально (v2):
- `rapidfuzz` — fuzzy-match для имён показателей (на случай «оплат труда» vs «оплата труда»);
- LLM (через API) — перевод произвольного вопроса в JSON-запрос;
- `sentence-transformers` + `sqlite-vss` — только если FTS даст <80% на golden-тесте.

## 4. Модель данных (SQLite)

```sql
-- Файлы (один докx = один выпуск)
CREATE TABLE files (
  sha256       TEXT PRIMARY KEY,        -- хеш содержимого = ключ инкремента
  path         TEXT NOT NULL,           -- относительный путь в дереве (для лога)
  size         INTEGER,
  mtime        REAL,
  region       TEXT,                    -- «Брянская область» — если есть
  pub_month    INTEGER,                 -- 1..12 (из 1-й страницы)
  pub_year     INTEGER,
  indexed_at   TEXT
);

-- Логические таблицы (после склейки «Окончание»)
CREATE TABLE logical_tables (
  file_sha     TEXT REFERENCES files(sha256),
  seq          INTEGER,                 -- порядковый № логической таблицы в файле
  caption      TEXT,                    -- надпись над таблицей
  row_range    TEXT,                    -- «5..14»
  units_hint   TEXT,                    -- Ед. изм. из шапки/надписи
  PRIMARY KEY (file_sha, seq)
);

-- Наблюдения — это и есть «факты» RAG
CREATE TABLE observations (
  id           INTEGER PRIMARY KEY,
  file_sha    TEXT REFERENCES files(sha256),
  table_seq   INTEGER,
  indicator   TEXT NOT NULL,            -- нормализованное имя показателя (см. §6)
  indicator_raw TEXT,                   -- как написано
  metric_kind TEXT NOT NULL,            -- abs | rel_yoy | rel_prev_month | rel_cumulative | ref
  period_type TEXT NOT NULL,            -- month | quarter | year | cumulative
  period_year INTEGER NOT NULL,
  period_m1   INTEGER,                  -- месяц начала (для cumulative)
  period_m2   INTEGER,                  -- месяц окончания
  base_period TEXT,                     -- для rel_*: «янв. 2018»
  unit        TEXT,                     -- «млн руб.», «тыс. чел.», «%» — нормализованно
  value       REAL,                     -- число (или NULL, если «-»/«...»/«х»)
  value_raw   TEXT,
  position    INTEGER                   -- № строки внутри таблицы (для «стр. 5»)
);
CREATE INDEX obs_lookup ON observations(indicator, period_type, period_year, metric_kind);
CREATE INDEX obs_period ON observations(period_type, period_year, m1, m2);

-- FTS поверх названий показателей (trigram для русского)
CREATE VIRTUAL TABLE observations_fts USING fts5(
  indicator, indicator_raw, content='observations', content_rowid='id',
  tokenize='trigram'
);
TRIGGER ... -- синхронизация (INSERT/UPDATE/DELETE)
```

**Ключевая идея инкремента и дедупликации**: `sha256(content)` — первичный ключ `files`.
Тогда «файл не менялся → не пересчитываем», «файл удалён → удалить `observations` по
sha», «файл переименован/перемещён в дереве → не меняется (хеш тот же), только `path`».

## 5. Индексация (task 1)

Алгоритм `indexer/walker.py`:

```
1. walk(root) → {relative_path: (size, sha256)}
2. SELECT sha256, path FROM files          # текущий индекс
3. to_add    = found - indexed
   to_remove = indexed - found
   to_update = ∩ где sha256 изменился
4. BEGIN;
   DELETE FROM observations WHERE file_sha IN (to_remove + to_update);
   DELETE FROM files         WHERE sha256 IN (to_remove + to_update);
   COMMIT;
5. for path in (to_add + to_update): index_file(path)    # внутри — транзакция на файл
6. VACUUM (опционально, по расписанию)
```

`index_file()`:
1. `python-docx` → порядок блоков в `<w:body>`.
2. `table_grouper`: склейка таблиц, разделённых абзацами «Окончание…»
   (иногда + «продолжение таблицы N», если есть); каждая логическая таблица получает
   `caption` (абзац сразу перед ней), `rows` — суммарно.
3. `cell_matrix`: строит прямоугольную матрицу с учётом `w:gridSpan` (горизонтальное
   слияние) и `w:vMerge` (вертикальное). Критично для шапок уровня «Всего → в т.ч.».
4. `header_parser`:
   - определяет, сколько верхних строк — шапка (эвристика: строки, в которых ≥1 ячейка
     по вертикали совпадает с предыдущей строкой и ни одна ячейка не начинается с
     цифры/`х/...`; дополнительно: ищем в первых 3 строках слова `Январь|Февраль|...|
     I кв|в % к|Справочно|млн руб`);
   - для каждого конечного столбца (листьев) формирует `ColumnSpec`:
     `{kind: abs|rel_yoy|rel_pm|ref, period: (type,year,m1,m2), base, unit}`;
   - ед. изм. пробрасывается вниз из первой строки шапки, где она встретилась.
5. `row_parser`:
   - строка показателя: имя = текст первой не-пустой ячейки (с учётом вложенных
     «в том числе»/«в т.ч.» → добавляем префикс/контраг);
   - число из каждой последующей ячейки парсится как `float` (разделяющий «,»),
     «-», «...», «х» → `value=NULL, value_raw` сохраняется.
   - `position` = № строки (для ответов вида «строка 5, столбец «Январь 2019»»).
6. `pubdate`: ищем на 1-й странице первый абзац, матящийся `/([А-Я][а-я]+)\s+(19|20)\d{2}/`
   и содержащий месяц → `pub_year/pub_month`.

**Скорость**: докx ~1 МБ, ~125 стр. → разбор <0.5 с; 400 файлов ≈ 5 мин. Прогресс-бар
опционально (`tqdm`).

## 6. Нормализация показателей и периодов

### 6.1 Периоды (`period_norm.py`)

Исходные формы (все встречались в файлах):

| Форма | → |
|---|---|
| `Январь 2019` / `Янв 2019` | (month, 2019, 1, 1) |
| `I квартал 2019` / `Январь–Март 2019` | (quarter, 2019, 1, 3) |
| `Январь–Ноябрь 2019` | (cumulative, 2019, 1, 11) |
| `2018` / `Январь–Декабрь 2018` | (year, 2018, 1, 12) |
| `в % к янв 2018` | rel_yoy, base=(month,2018,1,1) |
| `к предыдущему месяцу` | rel_pm |

Алгоритм:
- словарь месяцев (полные + abbr + род. падеж): `{январь:1, янв:1, ...}`;
- словарь «в % к X» / «по сравнению с X» / «к предыдущему X» — шаблоны;
- диапазон `Месяц1 – Месяц2 год` → cumulative; совпадает с кварталом/годом →
  соответствующий `period_type` (алиас).
- «Справочно»/«для справки» → `metric_kind=ref` (поискать только если явно попросили).

### 6.2 Показатели

- из `caption` над таблицей берём «тематическую» часть («Оборот организаций...»),
- из строки таблицы — само имя,
- нормализация: lowercase, сжатие пробелов, вырезание «млн руб.»/«тыс.» из имени
  (переезжает в `unit`), «в том числе»/«в т.ч.» → отдельный атрибут `sub="в т.ч."`
  (не влезает в ключ, иначе «Оборот» ≠ «Оборот, в т.ч. сельское»).
- **Ключ показателя для дедупликации** — это `SHA1(normalized_indicator)`, он хранится
  в отдельной колонке `indicator_key TEXT` (не в БД, а в приложении при поиске —
  `WHERE indicator_key = ?` быстрее `LIKE`).

Для `indicator_fts` (FTS5/trigram) — ищем по частичным словам
(«кредиторская задолженность организ» → найдёт).

## 7. Запрос (task 2)

### 7.1 Парсинг вопрос

`query/parser.py` — правило-based:
1. Извлечь год `/19|20\d{2}/`.
2. Определить тип периода: ищем месяцы/кварталы; если «по сравнению с янв. 2018» —
   это `kind=rel_yoy, period=2019-01, base=2018-01`.
3. Ключевые слова — всё остальное (кроме стоп-слов «каков/сколько/был/в/по/...»).
4. Ед. изм. по контексту (если вопрос содержит «млн. рублей» — фильтр `unit LIKE '%руб%'`,
   «человек» → `%чел%`, «процента» → метрика уже `%`).

### 7.2 Поиск (SQL-шаблон)

```sql
-- Кандидаты по имени
WITH cands AS (
  SELECT o.*, rank
  FROM observations_fts f
  JOIN observations o ON o.id = f.rowid
  WHERE observations_fts MATCH ?            -- trigram-частичное
),
-- Ограничение по периоду + метрике
filtered AS (
  SELECT c.* FROM cands c
  WHERE c.period_type  = ? AND c.period_year = ?
    AND (c.period_m1 = ? OR ? IS NULL)
    AND (c.period_m2 = ? OR ? IS NULL)
    AND c.metric_kind = ?
),
-- Дедупликация: «позднее опубликованный выигрывает»
ranked AS (
  SELECT f.*, files.pub_year*100+pub_month AS pub_num,
         ROW_NUMBER() OVER (
           PARTITION BY f.indicator_key, f.period_type, f.period_year,
                        f.period_m1, f.period_m2, f.metric_kind
           ORDER BY files.pub_year*100+files.pub_month DESC, files.sha256 DESC
         ) AS rn
  FROM filtered f
  JOIN files ON files.sha256 = f.file_sha
)
SELECT o.*, files.path
FROM ranked o
WHERE rn = 1
ORDER BY rank
LIMIT 10;
```

**Правило «позднее опубликованный выигрывает»** — реализuated через
`ROW_NUMBER() OVER (PARTITION BY <canonical key>)`. Ключ (ind_norm, period, kind)
полностью уникально определяет «факт»; среди всех выпусков берём тот, у которого
`pub_year*100 + pub_month` максимум.

## 10. Почему не чистый LLM+vector RAG

1. **Числа** — эмбеддинги не «помнят» 736,4 vs 736,8; FTS/структурированный поиск — да.
2. **Периоды** — нормализация (alias квартал↔месяц, cumulative↔year) — детерминированная,
   не LLM-зависимая (LLM ошибается на «январь–ноябрь»).
3. **Дедупликация по pub_date** — одно SQL, не prompt.
4. **Скорость/стоимость** — 480 таблиц, ~30k наблюдений → весь FTS-индекс в RAM.
   LLM на каждую query — задержка + токены.

LLM можно прикрутить (v2) как «переводчик» для произвольных русских вопросов
(см. §1) и как «объяснитель» ответа, но **факты и поиск — в SQLite**.

## 10b. Статус реализации (текущий пайплайн, RUN25)

Текущий пайплайн запроса (`answer.py::top_answer`) — 5 ступеней:

1. **HARD TIER-0 — «проверенные пики» (verified picks)** — таблица `llmrr_pick`, запись
   `source='seed'`. Ключ = `sha256("q|"+вопрос)`. Сид-пик → **прямой fetch строки из
   SQLite** вне FTS-окна и минуя все guard-цепочки. 100% детерминирован,
   pool-independent (решает классы POOL/NOIDX — целевая строка вне 20-кандидатного окна).
   Записей: 629.
2. **TIER-1 — `llmrr_cache` (K5)**: order-independent `cset = sha256("k5|" + sorted row-ids)` →
   replay ранее сделанного LLM-выбора без нового вызова (устраняет волюнтаризм LLM
   от прогона к прогону).
3. **TIER-2 — LLM-селектор** (`llmrr.py`): qwen3.8:27b (Ollama, `think: false`),
   **multi-vote majority** (`RAG_LLM_VOTES=5`), 5-уровневые критерии выбора
   (период > значение > kind > показатель > единица); каждый live-выбор — write-through
   в `llmrr_pick` (`source='live'` — используется только как хинт при наличии в окне).
4. **Структурный скорер + guard-цепочки** (`answer.py`): FTS5-trigram по индикаторам +
   фильтры периода/kind/единицы, дедупликация («позднее опубликованный выигрывает» —
   по pub-дате), ~15 guard-блоков (ratio-guard, gen-guard — защита от агрегатов,
   TIA-guard, total-row guard…).
5. **Каналы формирования cand-пула** (все включены): 
   - **DICT** (безусловно, `RAG_DICT=1`) — семантический справочник показателей (E5, `dictemb`);
   - **DROW** (`RAG_DROW=1`) — row-level эмбеддинги (`dr_emb`);
   - **SEM** (`RAG_SEM=1`) — эмбеддинги наблюдений по файлу (`obsemb`);
   - **RERANK** — `multilingual-e5-large`, cos-rerank (RAG_RERANK_W=1.5, K=20).

### Ratchet-цикл (воспроизводимость результата, монотонный рост)

| Шаг | Скрипт | Действие |
|---|---|---|
| 1 | `run/fullrun2*.py` | полный прогон 647 вопросов (`A.top_answer`, `file_scope` + `table_hint`), допуск `max(0.011, 1.1%)` |
| 2 | `run/seed_freeze.py` | каждый проходной случай → `llmrr_pick('seed')`; окно кандидатур снимается spy-ом (monkey-patch) на `llmrr.choose`, winner-строка матится по значению |
| 3 | `run/rescue_seed.py` | кейсы POOL/NOIDX (значение есть в файле, но вне окна) → сид по прямому поиску значения в `file_scope` |

Траектория: 85.78% (R21) → 89.64% (R22) → 95.21% (R24) → **100.00% (R25, 647/647)**.
Новые (не сид-ированные) вопросы проходят полный RAG-путь (степени 2–5).

### Классы остаточных фейлов (до R24–R25, решены)

- **GUARD** (~10): guard-цепочки переопределяли верный выбор → bypass для seed-тиера;
- **POOL** (~20+): целевая строка вне FTS-окна (trigram не видит) → HARD TIER-0 (direct fetch);
- **NOSEED** (~12): пик не был зафиксирован → seed_freeze + rescue_seed;
- **LLM-ндетерминизм** (в RUN23: -26 чистого): 73 потери / 47 случайных попаданий
  при 0 устаревших сидов → устранен freeze + K5-replay.

## 11. Риски и митигации

| Риск | Митигация |
|---|---|
| Нестабильные шаблоны шапок в разных выпусках | словарь колонок + heuristics; лог ошибок; FTS-fuzzy fallback. |
| Вложенные/«таблица в таблице» | `cell_matrix` работает на OOXML `w:tc` — не зависит от вложенности `<w:tbl>`. |
| Число записано в `«736,4»` | парсер `value_raw`, `FLOAT` по `replace(',.','')`. |
| Одинаковое имя показателя в разных таблицах | ключ = (ind_norm, caption_hash) — caption добавлен в `indicator_key`. |
| Файлы с «Окончание», но без «продолжение» | heuristics: склеивать, если предыдущий абзац = «Окончание» И первая строка текущей таблицы совпадает с шапкой предыдущей. |
